# 第三章实验报告：多道程序与分时多任务

## 实验目的

本实验围绕 rCore 第三章的多道程序与分时多任务展开。通过运行多个应用程序并观察它们与内核之间的交互，理解系统调用、任务管理和任务切换的基本过程。

本次重点完成了 `trace` 系统调用：读取或写入当前任务地址上的一个字节，以及查询当前任务的系统调用次数。

## 实验内容

### 系统调用计数

在任务管理器中增加系统调用计数表，为每个任务分别保存各系统调用编号对应的调用次数。进入系统调用分发函数后，先根据系统调用编号更新当前任务的计数，再执行对应的系统调用处理函数。

将计数按任务分别保存，可以避免不同任务的调用次数混在一起。查询计数时，读取当前任务对应的记录。

### `trace` 系统调用

`sys_trace` 根据请求类型执行操作：

- 请求类型 `0`：从 `id` 表示的地址读取一个 `u8`，并将读取结果作为返回值。
- 请求类型 `1`：将 `data` 转换为 `u8` 后写入 `id` 表示的地址，成功时返回 `0`。
- 请求类型 `2`：查询当前任务的系统调用计数，`id` 表示要查询的系统调用编号。
- 其他请求类型：返回 `-1`。

读取和写入字节时使用 `core::ptr::read_volatile` 与 `core::ptr::write_volatile`。

系统调用计数在分发前更新，因此查询 `trace` 系统调用次数时，本次查询也计入计数。

### 遇到的问题与解决方法

1、检查器目录不存在
第一次运行测试命令时，终端提示找不到 ci-user 目录。原因是本地尚未下载课程检查器。根据课程说明获取检查器和测试程序后，检查命令可以正常运行。

2、sys_trace 参数名称不一致
实现过程中，函数参数使用了 _trace_request、`_id` 和 _data，但函数体中使用的是 trace_request、`id` 和 data。参数名称不一致会导致编译错误。将函数声明中的参数名改为与函数体一致后，错误得到处理。

3、编辑器诊断与终端检查结果不一致
VS Code 中的 Rust Analyzer 曾显示 expected !, found ()。保存代码后，在 os 目录运行 cargo check，终端显示检查完成。之后运行官方检查器，trace 测试也显示通过。这个过程说明，遇到编辑器红线时，还需要结合实际编译和官方测试结果判断，不能只凭编辑器标记认定代码未通过。

### 实验总结
通过本次实验，我理解了系统调用统计需要与当前任务关联，并且应在统一的系统调用分发入口进行记录。这样既能统计不同系统调用，也能在查询时得到当前任务自己的调用次数。

我也理解了 trace 的基本工作方式：内核根据请求类型读取用户给定地址的数据、向该地址写入数据，或返回系统调用计数。
